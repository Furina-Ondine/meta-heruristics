# ADR-0010: 单点评估基础契约

## 状态

状态：Accepted

替代 [ADR-0006](0006-evaluation-performance-and-reproducibility.md)。

## 背景

ADR-0006 把单点评估定义为基础契约，并同时接受了可选的本机同步批量目标函数。当前 `IBatchObjectiveFunction` 要求调用方把所有候选位置组织成 candidate-major 的连续扁平缓冲区。该布局并不严格等同于 SoA，但会让采用交错对象、`double[][]` 或算法专用布局的种群产生整理和复制成本。

现有批量路径只批量调用目标函数，仍逐个验证候选和计算约束，并为目标值创建临时数组。仓库尚无算法实现、批量用例或基准数据证明这一公共快速路径有稳定收益。算法内部布局也尚未由 PSO、遗传算法和蝙蝠算法等实际实现验证。

## 决策

- 第一波只保留 `IObjectiveFunction.Evaluate(ReadOnlySpan<double>)` 单点评估契约。
- 删除 `IBatchObjectiveFunction`、`ContinuousProblem.EvaluateBatch` 和 `OptimizationRunContext.EvaluateBatch`。
- 算法通过 `OptimizationRunContext.Evaluate` 逐个候选评估，以统一候选验证、约束汇总、取消和评估计数。
- Core 不规定种群使用 AoS、SoA、矩形数组、交错数组或对象集合；具体算法根据自身状态选择布局。
- 未来即使重新引入批量能力，也必须是算法显式选择的可选路径；不支持的算法和目标函数继续使用单点评估。
- 重新引入前必须用实际算法和目标函数测量数据布局转换、分配、约束处理和总运行时间，不能只测目标函数调用本身。
- 每个 run 继续使用独立 seed 和 `Random`；禁止全局随机状态和当前时间播种。
- run 的 seed 和随机序列不随 RunGroup 拆分、调度顺序或实验并发度变化。
- 性能改动必须有 BenchmarkDotNet 数据或分配分析，并保留清晰、正确的单点基础路径。
- 第一波不引入远程、集群或 GPU 评估后端。

## 替代方案

- 保留批量接口但让所有算法自行决定是否调用：兼容性最好，但会继续承诺未经实际布局和基准验证的公共缓冲区形状。
- 只删除 `IBatchObjectiveFunction`，保留退化为循环的 `EvaluateBatch`：调用便利，但容易继续被理解为 Core 的统一批量后端。
- 为不同 AoS/SoA 布局同时设计批量接口：覆盖面更大，但会在算法落地前扩大 API 和测试矩阵。
- 强制所有算法采用同一种群布局：有利于某一类批量后端，却不能自然表达蝙蝠算法等算法专用的多组个体状态。

## 后果

首版评估 API 更小，算法可以在不复制位置缓冲区的情况下采用最自然的数据布局。短期内无法利用一次调用评估多个候选的目标函数后端，但也不会为未经验证的快速路径承担稳定兼容契约。

ADR-0006 中关于随机性、确定性、基准和本机执行的规则由本 ADR 继续保留；只有批量评估决策被撤回。

## 重新评估条件

当至少一个实际算法和目标函数显示单点评估成为主要瓶颈，并且基准能够证明某种批量契约在包含布局转换、验证和约束处理后仍有稳定收益时，通过新 ADR 设计可选批量能力。
