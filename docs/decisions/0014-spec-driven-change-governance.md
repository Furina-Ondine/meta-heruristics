# ADR-0014: Spec-Driven 变更治理

## 状态

Accepted

## 背景

仓库已经具有工程规范、ADR、设计稿、实施计划、测试和面向不同读者的文档，但具体功能设计长期被视为过程档案。代理可以在缺少已批准行为规格的情况下直接从模糊意图生成实现，容易把常见但不符合本项目风格的防御性编程、重复抽象和职责放置带入代码。

现有变更流程还缺少统一的责任替代、连带影响和需求到验证的追踪。职责从 Core 迁移到 Experiments 等更合适的层后，旧抽象可能因未被主动审计而继续存在。文档和 XML 注释也因多处手工复述同一契约而发生漂移。

需要让高风险变更在编码前形成可批准的行为规格和技术计划，同时避免小型内部修复承担完整文档流程。

## 决策

- `ENGINEERING.md` 是跨功能持续有效的工程宪法；Accepted ADR 解释长期或跨功能决策；Approved 或 Implemented Spec 定义对应功能的公共意图和行为。
- 新功能规格保存在 `docs/specs/SPEC-NNNN-feature-name/`，包含 `spec.md`、`plan.md`、`tasks.md` 和 `verification.md`。`docs/superpowers/` 保留为历史过程档案，不再承载新的权威功能规格。
- 公共 API、可观察行为、项目职责、策略与执行抽象、状态、随机性、数值语义、热路径性能、兼容策略或跨运行时项目的变化必须走完整 SDD：Spec、澄清、用户批准、Plan、用户批准、Tasks、实现和 Verification。
- 不改变公共行为、职责、抽象、数值、状态、并发和确定性契约，且已有权威资料明确预期的局部内部修改，可以采用经用户批准的轻量设计。发现隐藏复杂度时只能升级到完整 SDD。
- Spec 使用稳定的 `FR` 和 `NFR` 编号；Plan、Tasks、测试、基准和 Verification 必须能够追踪到这些需求。
- 新设计必须调查现有实现、重复概念和跨代码、测试、示例、基准与文档的影响。职责迁移时默认删除失去独立价值的旧入口、转发层和兼容壳；保留需要真实消费者、期限和删除条件。
- 参数、返回值、异常、所有权和成员级特殊语义只在源码 XML 注释中维护，并由生成式 API Reference 呈现。手写 API 文档只提供能力和入口地图。
- 实现与 Approved Spec 冲突时，当前代码不自动胜出。必须报告冲突，由用户决定修正实现、修订 Spec 或用新 ADR 替代既有决策。

## 替代方案

- 所有变更都走完整 SDD：一致性最强，但会让拼写、格式和明确的小修复承担不成比例的成本。
- 只依赖 ADR 和 `AGENTS.md`：文档较少，但不能表达逐功能验收条件，也无法建立需求、任务和测试追踪。
- 直接采用某个外部 SDD 工具的默认工作流：启动较快，但会在验证本项目需求前引入大量模板和代理命令。仓库先建立工具无关的契约，试点后再评估工具。

## 后果

高风险变更需要两次明确的用户批准，编码启动会稍晚，但需求、架构和删除范围会在成本较低时暴露。新 change package 和验证器增加少量维护成本，也提供了状态、链接和追踪的机械检查入口。

历史 `docs/superpowers/` 不批量迁移，避免为已完成工作制造虚假状态。新旧体系并存期间，索引必须明确它们的权威差异。

## 重新评估条件

当至少三个真实 change package 完成并积累流程数据，或模板负担明显超过减少的返工成本时，重新评估风险分类、产物数量和自动化方式。引入 Spec Kit 或其他工作流工具时，不得改变本 ADR 的批准与权威语义，除非由新 ADR 替代。
