# Metaheuristics.NET 工程治理文档设计

## 1. 目的

Metaheuristics.NET 需要一套同时面向人类贡献者和 AI 代理的工程治理文档，以确保代码风格、架构边界、职责划分、质量门槛和技术路线在长期演进中保持一致。

本设计不把所有规则堆入 `README.md`，而是将项目介绍、当前架构、长期工程契约和历史决策分开维护。每类文档只有一种主要职责，从而减少内容重复和规则分叉。

## 2. 文档体系

仓库增加以下文档结构：

```text
README.md
ENGINEERING.md
AGENTS.md

docs/
├── architecture/
│   └── overview.md
├── decisions/
│   ├── README.md
│   ├── 0001-platform-and-toolchain.md
│   ├── 0002-library-scope-and-evolution.md
│   ├── 0003-project-and-package-boundaries.md
│   ├── 0004-composition-and-execution-model.md
│   ├── 0005-candidate-objective-and-constraints.md
│   ├── 0006-evaluation-performance-and-reproducibility.md
│   └── 0007-versioning-and-release.md
└── superpowers/
    ├── specs/
    └── plans/
```

各类文档的职责如下：

- `README.md`：面向首次接触项目的读者，说明项目定位、能力范围、成熟度、快速开始和路线图摘要；
- `ENGINEERING.md`：工程规范的权威来源，规定持续有效的架构、编码、性能、测试和变更规则；
- `AGENTS.md`：为 AI 代理提供简明执行入口，并明确要求遵守 `ENGINEERING.md` 和相关 ADR；
- `docs/architecture/overview.md`：描述当前系统结构、组件职责、依赖关系和主要运行流程，不解释历史选择；
- `docs/decisions/`：通过架构决策记录解释重要选择的背景、替代方案、后果和重新评估条件；
- `docs/superpowers/specs/` 与 `docs/superpowers/plans/`：保留具体变更的设计和实施过程，不充当长期工程规范。

现有 `2026-08-19-project-foundation-design.md` 继续作为项目基础形成过程的设计档案，但不再承担长期规范职责。

## 3. 权威性与一致性

文档按以下方式协作：

1. `ENGINEERING.md` 规定当前必须遵守的工程契约；
2. 状态为 `Accepted` 的 ADR 解释契约和架构选择的原因；
3. 新 ADR 可以显式替代旧 ADR，变更生效时同步更新 `ENGINEERING.md` 和架构概览；
4. 架构概览只描述变更完成后的当前状态；
5. `README.md` 仅提供摘要并链接到详细文档；
6. `AGENTS.md` 不复制整份规范，只列出代理进入仓库时必须执行的检查和权威文档链接。

如果实现、概览和已接受决策不一致，不通过增加模糊例外来掩盖差异。贡献者必须确认是实现偏离规范，还是原决策需要被新 ADR 替代。

## 4. 工程规范内容

`ENGINEERING.md` 至少包含以下规则。

### 4.1 依赖与职责边界

- `Metaheuristics.Core` 不引用其他仓库项目；
- `Metaheuristics.Algorithms` 和 `Metaheuristics.Experiments` 只依赖 `Core`，且彼此不依赖；
- `Examples`、`Tests` 和 `Benchmarks` 只能按既定依赖图引用运行时项目；
- 论文业务模型、实验专用逻辑和领域解码不进入运行时包；
- `Core` 定义稳定契约，具体算法不得反向污染核心抽象。

### 4.2 API 与扩展倾向

- 优先使用强类型接口、显式依赖和组件组合；
- 用户负责选择并装配问题、算法和策略，库负责运行生命周期；
- 单次运行允许传入实例，批量实验使用强类型工厂创建隔离实例；
- 不引入全局字符串注册表、服务定位器或依赖字符串类型名恢复任意组件的机制；
- 不为尚未进入实施路线图的表示类型、目标类型或计算后端提前建立复杂抽象。

### 4.3 状态、并发与随机性

- `Optimizer` 保存算法定义和不可变参数，可以安全复用；
- `Session` 独占单次运行的种群、随机流和临时缓冲区，不保证线程安全；
- 禁止使用 `Random.Shared`、当前时间播种或跨运行共享可变状态；
- 并发度变化不得改变每个独立 run 的种子和随机序列；
- 池化资源必须具备清晰的所有权、清理和释放规则。

### 4.4 数值正确性

- 输入参数、边界、目标值和约束结果必须经过明确验证；
- `NaN`、无穷值、无效范围和容差不得被静默传播；
- 等式约束必须使用显式绝对容差和相对容差；
- 约束判定、候选比较与候选修复保持独立职责；
- 数值异常的公共行为必须有文档和测试定义。

### 4.5 性能纪律

- 先保证正确性、边界清晰和可测试性，再优化热路径；
- 热路径优化必须有 BenchmarkDotNet 数据或分配分析作为依据；
- `Span<T>`、池化、批量评估和并行化必须保留正确、清晰的基础路径；
- 不因理论上的未来后端需求引入远程执行、集群调度或 GPU 抽象；
- 性能改动不得破坏确定性、资源安全和公开语义。

### 4.6 测试与质量门槛

- 新增或改变公共行为时先定义可观察契约，并由自动化测试覆盖；
- 核心契约需要正常路径、边界条件、无效输入和取消行为测试；
- 算法实现需要标准测试函数、固定种子复现、并发隔离和数值安全测试；
- 性能承诺需要对应基准，避免只凭实现形式声称更快；
- 合入前至少执行 Release 配置的 restore、build 和 test；
- 公共 API、示例和文档必须随行为变化同步更新。

### 4.7 代码风格

- 遵循标准 .NET 命名、API 设计和异步命名约定；
- 保持 nullable、编译器分析、确定性构建和警告视为错误；
- `.editorconfig` 是可机械执行的格式与风格规则来源；
- 初期不引入沉重的 StyleCop 规则集，仅在真实一致性问题无法由现有工具解决时重新评估；
- 注释解释原因、约束和不明显的数值处理，不逐句复述代码。

### 4.8 变更治理

以下变化必须先形成或替代 ADR：

- 改变项目或包的依赖方向；
- 改变公共执行模型、组件构造职责或状态所有权；
- 改变候选、目标值、约束或比较语义；
- 引入新的计算后端或跨进程能力；
- 改变可复现性承诺、性能策略或版本发布规则；
- 对既定路线图进行顺序或范围上的实质调整。

局部实现、内部重构和不改变公共行为的缺陷修复不要求新增 ADR。

## 5. AI 代理规则

根目录 `AGENTS.md` 保持简洁，并要求代理：

1. 修改前阅读 `ENGINEERING.md`、架构概览和与任务相关的 ADR；
2. 不绕过项目依赖、状态隔离和数值安全规则；
3. 公共行为和架构变化必须先形成设计，必要时新增 ADR；
4. 实现功能或修复缺陷时以自动化测试定义行为；
5. 不覆盖或回退不属于当前任务的用户修改；
6. 完成前运行与风险相称的构建、测试和基准验证；
7. 发现规范、实现与 ADR 冲突时报告冲突，而不是自行选择方便的解释。

`AGENTS.md` 只摘要执行要求并链接到权威规范，以避免人类规范和代理规范分别演进。

## 6. 架构概览

`docs/architecture/overview.md` 描述当前而非预想中的系统，包含：

- 六个项目的职责；
- 已批准的单向依赖图；
- `Problem + Optimizer -> Runner -> Session -> Result` 的单次运行数据流；
- `Experiments -> typed factories -> isolated runs -> aggregate` 的批量实验流程；
- 当前公开扩展点和明确不在首版范围内的能力；
- 与 `ENGINEERING.md`、ADR 和 API 文档之间的链接。

架构概览不复制每项决策的详细论证。发生架构变更时，它与实现同一次变更更新。

## 7. 架构决策记录

`docs/decisions/README.md` 规定统一 ADR 格式：标题、状态、背景、决策、替代方案、后果和重新评估条件。初始状态使用 `Accepted`；被后续决策替代时使用 `Superseded` 并互相链接；已经否决但需要保留历史原因的方案使用 `Rejected`。

首批 ADR 记录以下已确定选择：

1. **平台与工具链**：.NET 10、`net10.0`、`.slnx`、集中包版本管理、xUnit v3、Microsoft Testing Platform 和 BenchmarkDotNet；
2. **库范围与演进顺序**：连续 `double` 候选和标量 `double` 目标值起步，随后依次推进由 Objective Policy 定义能力的泛型单目标值、多目标、二进制与排列表示；泛型值不被强制要求实现 `IComparable<T>`，首版不支持远程、集群和 GPU；
3. **项目与包边界**：`Core`、`Algorithms`、`Experiments`、`Examples`、`Tests` 和 `Benchmarks` 的职责及引用关系；
4. **组件构造与运行模型**：用户装配、库管理生命周期，单次实例、批量强类型工厂，以及 `Optimizer`、`Session` 和 Runner 的分工；
5. **候选、目标值与约束**：首版采用连续 `double` 向量和标量 `double`，支持优化方向、可行性优先、归一化加权违背量和带容差的等式约束；
6. **评估、性能与可复现性**：单点评估为基础契约，本机同步批量评估为可选快速路径，独立随机流和基准驱动优化；
7. **版本与发布**：所有可发布包采用统一版本，整体遵循 Semantic Versioning 2.0.0。

## 8. 版本与发布规则

`Metaheuristics.Core`、`Metaheuristics.Algorithms` 和 `Metaheuristics.Experiments` 使用相同版本号，并在一次发布中锁步发布。即使某个包在该版本没有实质代码变化，也随其余运行时包发布同一版本，以提供唯一且明确的兼容组合。

版本号采用 `MAJOR.MINOR.PATCH`：

- `MAJOR`：不兼容的公共 API 或行为变化；
- `MINOR`：向后兼容的新功能；
- `PATCH`：向后兼容的缺陷修复。

预发布版本使用 SemVer 标识，如 `0.1.0-alpha.1`、`0.1.0-beta.1` 和 `1.0.0-rc.1`。

在 `1.0.0` 前，公共 API 仍处于初始开发阶段。破坏性变化至少提升 `MINOR`，并在发布说明中明确记录。达到 `1.0.0` 后，不兼容变更必须提升 `MAJOR`；向后兼容的新能力提升 `MINOR`；向后兼容的修复提升 `PATCH`。

纯文档或仓库维护变更不必产生包版本。发布自动化和变更日志格式在首次 NuGet 发布设计中单独确定，本次不提前引入工具。

## 9. 实施与验证范围

实施阶段只增加和调整文档，不改变运行时代码或公共 API：

- 创建 `ENGINEERING.md` 和 `AGENTS.md`；
- 创建架构概览和 ADR 索引；
- 写入七份首批 ADR；
- 精简 `README.md` 中过于详细且会重复维护的架构内容，改为摘要和链接；
- 保留现有基础设计与脚手架计划；
- 检查所有相对链接和文档之间的职责一致性；
- 运行 Markdown 文本检查、`git diff --check`，并重新执行解决方案 Release 构建和测试，确认文档变更没有破坏仓库状态。

本次不引入文档站点生成器、ADR CLI、发布自动化、StyleCop 或新的 NuGet 依赖。
