# Spec-Driven 开发工作流设计

## 状态

Approved

批准日期：2026-08-27。

## 背景

项目已经具有工程规范、架构概览、ADR、功能设计、实施计划、测试和面向用户的文档，但现有功能设计被定位为过程或历史档案，尚未成为约束实现的权威输入。实际开发中已经出现两类重复偏差：

- Core 对策略拥有的数据进行重复防御性验证，例如在 Initializer 和 Repair 之外再次验证候选位置。这与项目追求的性能和策略组合风格不符。
- 职责迁移时只增加新实现，没有系统审计并删除被替代的旧抽象。例如批量 run 的职责进入 Experiments 后，Core 中相似结构失去独立价值却仍可能继续存在。

本设计建立适合当前仓库的 Spec-Driven Development（SDD）工作流。目标不是增加文档数量，而是把用户意图、架构约束、技术方案、实施任务和验证证据连成可以审查的闭环。

## 目标

- 在编码前暴露需要用户决定的需求、架构和数值语义，减少代理依靠惯例猜测。
- 让公共行为、责任边界和替代关系成为可批准、可追踪的规格。
- 强制分析跨项目、测试、示例、基准和文档的连带影响。
- 让每条需求能够追踪到实施位置和自动化证据。
- 对高风险变化采用完整 SDD，同时为低风险内部修改保留轻量流程。
- 让 README、User Guide、Developer Guide 和 API 文档分别服务明确的读者任务，减少重复且无法形成学习路径的内容。
- 让公共 API 注释提供准确的成员契约，而不是以机械覆盖率制造无信息量文档。

## 非目标

- 本设计不引入运行时插件发现、程序集扫描、字符串注册中心或服务定位器。
- 本设计不要求所有拼写、格式或无语义维护都创建完整规格。
- 本设计不选择或安装特定 SDD 工具；工作流首先由仓库内的 Markdown 契约定义。
- 本设计不在本次变更中重写现有代码、历史规格、ADR 或测试。
- 本设计不要求手工维护一份与 XML 注释重复的成员级 API Reference。

## 架构风格

### 显式策略组合

本项目的“插件化”指基于强类型接口和策略模式的显式组合。Core 提供维持运行生命周期所需的最小稳定协议；用户通过实现并组装 Objective、Constraint、Initializer、Repair、Stopping Condition、Optimizer 等策略扩展系统。库不解释策略的私有数据，也不重复拥有策略职责。

### 最小必要验证

Core 只验证维持自身协议所必需的不变量：

- 可以在构造阶段验证一次的配置，不得在热路径重复验证。
- 候选位置是否合法、是否越界，由 Initializer 和 Repair 负责；Core 不重复验证。
- 目标值 `NaN` 违反比较协议，必须在统一评估入口失败。
- 目标值的正负无穷是合法值，并按优化方向比较。
- 约束违背量必须非负且不能为 `NaN`；正无穷可以表示无界的不可行程度。
- 策略违反其职责时，不由 Core 猜测用户意图或进行静默修复。

上述数值语义改变现有工程契约，实施时必须由新 ADR 正式决定并由测试定义。

### 单一职责归属

一个运行概念只能有一个权威所属层。Core、Algorithms、Experiments 和调用方之间的职责必须能够明确回答“谁拥有、谁驱动、谁验证”。新功能不得在多个层重复建立相同的编排或生命周期模型。

### 替代必须完成闭环

职责迁移或设计被替代时，默认删除失去独立价值的旧类型、旧入口、转发层、兼容壳、测试和文档。公共 API 的破坏性不是保留无消费者抽象的充分理由。只有存在已确认的真实兼容需求时才允许保留，并必须记录消费者、期限和删除条件。

## 文档信息架构

文档按读者要完成的任务组织，而不是按当前源代码结构重复描述同一契约。每份文档必须具有明确的首要读者、问题范围和不承担的职责。

| 文档 | 首要读者与必须回答的问题 | 不承担的职责 |
| --- | --- | --- |
| `README.md` | 让首次接触者快速判断项目是什么、当前能做什么、成熟度如何、怎样运行最短示例以及下一步读什么。 | 完整教程、成员级 API、架构论证。 |
| User Guide | 帮助使用内置算法解决优化问题的用户建立概念模型并完成第一次单次运行，随后学习结果、常见变化和批量实验。 | 内部实现、历史决策、逐成员参考。 |
| API Overview | 按用户任务给出能力分组、顶层入口、核心类型关系和 Reference 导航。 | 参数、异常、属性和重载的重复清单。 |
| 生成式 API Reference | 从程序集签名和 XML 注释呈现类型与成员的精确调用契约。 | 端到端教学和架构理由。 |
| Developer Guide | 帮助扩展或维护项目的人实现策略与算法，并理解项目职责、生命周期、状态、随机性、性能和变更影响规则。 | 新用户的第一次使用教程、成员清单。 |
| `ENGINEERING.md` | 定义持续有效且不可静默违反的跨功能工程契约。 | 用户教程和逐功能设计。 |
| ADR | 解释长期或跨功能架构选择的背景、替代方案与后果。 | 调用教程和成员参考。 |
| Spec | 定义一项功能的公共意图、行为、责任和成功标准。 | 通用教程和成员级参考。 |

### User Guide 学习路径

User Guide 的首要读者是使用内置算法解决一个优化问题的人，固定按以下认知顺序组织：

1. 说明库当前能解决的问题，并用具体输入、优化过程和输出建立预期。
2. 给出单次优化与批量实验两条顶层使用路径及各自入口。
3. 先解释第一次运行必需的 Problem、Objective、Optimizer、Stopping Condition 和 Result；Initializer、Repair、Constraint、RunGroup 等概念在实际需要时再引入。
4. 提供从问题定义到读取结果的第一个完整可运行例子，并解释每个对象在整体流程中的作用。
5. 按任务说明最大化、自定义边界与 Repair、约束、停止条件和固定 seed 等常见变化。
6. 先解释批量实验解决的问题，再引入 Case、repetition、RunGroup 和并发。
7. 将具体成员查询、策略或算法扩展、架构决策分别引导到 API Reference、Developer Guide 和 ADR。

### 内容权威与去重

一项事实只能有一个权威位置。其他文档可以提供一句与当前读者任务相关的上下文提示并链接权威说明，不得复制整段契约。每段手写内容在评审时必须回答：

- 目标读者是谁，他正在完成什么任务；
- 该事实的权威位置在哪里；
- 此处需要解释、摘要还是只提供链接；
- 删除此段后，读者是否仍能沿学习路径找到答案。

参数、返回值、异常、所有权、生命周期和特殊成员语义以源码 XML 注释为唯一内容来源。成员级 API Reference 必须从程序集签名和 XML 注释生成；手写 API 文档只保留 API Overview，不再逐类型复述 XML 内容。

### 文档可理解性验收

文档不按字数、文件数或重复覆盖率验收。首次使用者读完 README 和 User Guide 后，应能不阅读源码回答：

- 项目当前能做什么以及明确不支持什么；
- 单次优化和批量实验分别从哪里进入；
- 第一次运行最少需要创建哪些对象；
- 最佳目标值和位置从哪里读取，何时必须复制；
- 怎样替换一项策略；
- 查询具体参数、异常和扩展规则时应前往哪份文档。

项目作者无法沿文档快速回答上述问题时，即使内容没有单项事实错误，也不能认为文档质量合格。

## XML 与代码注释质量

### 成员级单一来源

XML 注释是成员级 API Reference 的唯一内容来源。公共 API 变更时，源码签名、XML 契约和对应测试必须在同一变更中保持一致；XML 注释失真按公共 API 缺陷处理。User Guide 和 API Overview 不复制成员的参数、异常或完整生命周期说明。

### 信息增量原则

除属性外，注释必须提供名称、类型和签名无法可靠表达的信息，例如：

- 使用目的、适用场景和职责边界；
- 参数范围、单位、特殊值和组合约束；
- 返回值的业务含义、所有权、生命周期和失效时间；
- 状态变化、副作用、分配和热路径特征；
- 线程安全、可重入性、随机性、确定性和调用顺序；
- `NaN`、Infinity、容差等特殊数值语义；
- 精确异常条件、误用风险和非显然权衡。

类、结构、记录、接口、构造函数、方法、事件、委托以及非显然的枚举不得只把标识符改写为一句自然语言，也不得逐句复述实现。

### 属性例外

属性允许最低限度地描述“它是什么”，例如“获取算术平均值”或“获取种群大小”。这只是简单属性的合格下限。属性存在以下任一非显然语义时，必须补充完整契约：

- 合法范围、默认值、单位、特殊值或可空条件；
- 快照、只读视图或借用缓冲区的所有权区别；
- 失效时间、分配行为、线程安全或状态依赖；
- 设置后的可变性、值不存在时的行为或特殊数值语义。

因此，属性可以说明“它是什么”；其他公共符号还必须解释“为什么需要、怎样正确使用或有什么约束”。

### 内部注释

内部注释说明原因、约束和不明显的算法处理，不复述下一行代码。性能注释必须说明避免的成本或保持的不变量，并与基准或明确实现事实一致。

### 注释质量检查

新增或修改的注释必须通过以下检查：

1. **签名复述检查**：除属性例外外，只根据标识符即可自动生成的注释不合格。
2. **删除检查**：删除后若调用者不会失去正确使用 API 所需的信息，则应删除或重写。
3. **决策检查**：注释应帮助调用者决定怎样调用、何时复制、能否并发或怎样处理失败。
4. **准确性检查**：每项事实必须能在实现、测试、Approved Spec 或 Accepted ADR 中找到依据。

自动化验证 XML 格式、代码引用、Reference 生成、示例编译和已删除类型残留；信息增量仍由代码审查判断。注释数量和公共成员注释覆盖率不作为独立质量指标。

## 风险分级

### 完整 SDD

变更满足下列任一条件时，必须采用完整流程：

- 新增、删除或改变公共 API；
- 改变用户可观察行为；
- 改变项目职责、依赖方向或跨层所有权；
- 新增、替代或删除策略接口、生命周期或执行抽象；
- 改变状态所有权、线程安全、随机性或确定性；
- 改变候选、目标、约束、比较或修复语义；
- 影响热路径性能或提出性能主张；
- 变更跨越两个以上运行时项目；
- 新设计与现有实现存在重复概念；
- 调整路线图、兼容策略或支持范围；
- 需求仍要求代理猜测会影响结果的行为。

完整流程为：

```text
Spec → Clarify → 用户批准 → Plan → 用户批准
     → Tasks → Implement → Verify → Implemented
```

### 轻量设计

变更只有在同时满足以下条件时才能使用轻量流程：

- 不改变公共 API 或可观察行为；
- 不改变职责所属层，不引入新抽象；
- 不改变数值、状态、并发或确定性契约；
- 现有规格、ADR 或测试已经明确期望行为；
- 影响局限于一个模块；
- 可以用明确的自动化验证证明完成。

轻量流程在对话中记录问题、修改意图、影响范围和验收方式，经用户批准后实施。发现隐藏复杂度时只能升级到完整 SDD，不能在实施中降级。

### 机械变更

拼写、格式、链接修复和无语义批量整理可以采用机械流程，但必须确认不改变公共名称、行为或规范含义。

## 规格产物

每个完整 SDD change package 使用稳定编号，并保存 `spec.md`、`plan.md`、`tasks.md` 和 `verification.md`。Spec 是该功能公共意图和行为的权威来源；Accepted ADR 继续解释跨功能或长期架构决策；架构概览继续报告实现现状。

### Spec

Spec 只定义 why 和 what，固定包含：

1. 元数据：编号、状态、日期、批准人、替代关系和相关 ADR。
2. 问题与动机：当前问题及具体证据。
3. 目标与非目标：完成结果和明确排除项。
4. 架构契合：对策略组合、验证、职责、替代、性能和确定性原则的符合性。
5. 信任与责任边界：数据或行为的责任方、Core 是否验证、违反契约的结果。
6. 功能需求：使用稳定的 `FR-NNN` 编号，包含前置条件、触发行为、预期结果、边界情况和验收标准。
7. 非功能需求：使用 `NFR-NNN` 编号，包含测量方式、阈值和证据类型。
8. 职责与替代关系：新增、被替代、必须删除及明确保留的概念，以及完成后的唯一所属层。
9. 成功标准：从用户和架构结果定义完成，不以“代码已写”作为成功标准。
10. 假设与待澄清问题：影响公共行为的待定项未解决前不得批准。
11. 批准记录：批准人、日期和明确接受的风险。

Spec 状态为：

```text
Draft → Clarifying → Approved → Implementing
      → Verifying → Implemented → Superseded
```

`Approved` 后不得静默修改需求。实施中发现规格错误时，状态退回 `Clarifying`，修改后重新批准。

### Plan

Plan 只基于 Approved Spec 制订，固定包含：

1. Spec 基线和覆盖的 `FR/NFR`。
2. 当前实现调查：相关入口、调用链、职责、重复概念、测试、示例、文档、基准及已知冲突。
3. 至少两个合理方案的权衡和选择理由。
4. 目标职责模型：每个概念变更前后的所属层。
5. 信任和验证设计：每项验证的位置、频率、热路径成本、保护的不变量及失败语义。
6. API 和行为的新增、修改、删除、破坏性变化、迁移方式及保持不变项。
7. 替代与清理计划：被取代结构、旧测试和文档、残留搜索方法，以及任何保留项的真实消费者和期限。
8. 连带影响矩阵：Core、Algorithms、Experiments、Examples、Tests、Benchmarks、XML 文档、用户/API 文档、ENGINEERING 和 ADR。无影响也必须说明理由。
9. 需求到测试或基准的验证设计。
10. 风险、早期发现方式和退回规格澄清的条件。
11. 是否触发 ADR 及判断依据。

Plan 经用户批准后才能生成 Tasks。Tasks 不得重新选择架构方案。

### Tasks

任务按需求纵向拆分，使同一需求的实现、测试和必要文档一起完成。每项任务包含：

- `TNNN` 编号和状态；
- 覆盖的 `FR/NFR`；
- 依赖任务和影响区域；
- 实施内容及明确不做的内容；
- 完成条件、验证命令和实际验证结果。

出现以下情况必须停止实施并退回 Spec 或 Plan：

- 需要未批准的公共类型、抽象或行为；
- 发现 Plan 未处理的重复概念；
- 实际影响与影响矩阵不符；
- 需要新的热路径验证；
- 只能通过放宽契约或绕过工程规则使测试通过；
- 实现要求对用户意图作新的设计判断。

### Verification

验证报告必须提供：

- `FR/NFR → 实现位置 → 测试或基准 → 文档 → 结果` 的追踪表；
- 被替代概念的预期处理、残留搜索和结果；
- 策略职责、重复验证、无消费者抽象和职责所属层的架构一致性检查；
- Restore、Release Build、Tests、Format、文档链接及适用基准的实际结果。

只有所有需求有证据、所有任务完成、被替代结构已处理、工程验证通过且跨产物无未解释冲突时，Spec 才能进入 `Implemented`。

## 权威性与冲突处理

- `ENGINEERING.md` 是跨功能持续有效的项目宪法。
- Accepted ADR 解释长期或跨功能架构选择。
- Approved/Implemented Spec 定义对应功能的公共意图和行为。
- Plan 和 Tasks 定义某次实现转换，不覆盖 Spec 或 ADR。
- 架构概览和 API 文档报告已经实现的现状。
- 实现与 Approved Spec 冲突时，不以当前代码自动胜出；先报告冲突并决定修正实现、修订 Spec 或新增替代 ADR。

## 实施边界

本设计获批后的实施计划应至少覆盖：

- 建立 change package 目录、统一模板和状态规则；
- 将 `AGENTS.md` 与工程规范接入风险分类和批准门；
- 增加规格、计划、任务和验证之间的追踪检查；
- 增加本地或 CI 文档链接、状态、索引和替代关系检查；
- 建立文档内容所有权、读者任务和去重检查清单；
- 将手写的逐成员 API 文档收敛为 API Overview，并选择从 XML 生成成员级 Reference 的方式；
- 建立 XML 注释的信息增量、属性例外和准确性审查规则；
- 选择一个真实的高风险变更作为首个试点，而不是立即迁移全部历史档案；
- 通过试点复盘模板负担和拦截偏差的效果，再决定是否引入 Spec Kit 等工具。

## 成功标准

- 高风险任务在编码前具有用户批准的公共行为、责任边界和替代关系。
- Plan 能明确识别现有重复概念及所有连带影响区域。
- 每条功能和非功能需求都能追踪到自动化证据。
- 代理在遇到未批准设计判断时停止并请求澄清，而不是自行补全。
- 职责迁移完成后，不遗留没有真实消费者的旧抽象。
- 轻量变更不承担完整 SDD 的文档成本。
- README、User Guide、API Overview、Developer Guide 和生成式 Reference 具有可区分的读者任务，不再手工复制成员契约。
- 新用户能从文档识别两条顶层入口、第一次运行所需概念和后续查询路径。
- 除简单属性例外外，公共 API 注释提供签名之外的正确使用信息，且不存在与当前实现冲突的陈旧契约。
