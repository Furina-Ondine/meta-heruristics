## 问题与动机

Core 的 `CandidateRepairs.ReflectCandidateRepair` 与 Algorithms 的私有 `VectorOps` 都使用运行时可用的 `Vector512<T> → Vector256<T> → Vector128<T> → scalar` 固定宽度级联。该策略已分别通过 SPEC-0004、SPEC-0005 和 ADR-0016 获得行为与性能证据，但其硬件判断、完整块条件、索引推进、宽度缩窄和标量尾部仍由各热路径手写。

当前重复已经覆盖 Core 与 Algorithms 两个运行时项目以及 PSO、Firefly、Reflect 等不同运算。继续手写会使增加或修正统一 SIMD 模式时必须同步修改多个位置，例如宽度策略、元素类型、加载/存储方式、尾部规则或未来经测量批准的对齐处理。遗漏任一位置会形成行为或性能漂移；将循环改为运行时委托、接口或通用策略则可能引入调用、分派、状态传递或阻碍内联，不能满足零运行时开销要求。

需要一个只在编译期存在的仓库私有生成设施：由单一权威定义产生各消费程序集自己的完全展开 C#，使生产程序集继续拥有私有 SIMD 代码和既有职责，同时不为统一维护引入运行时抽象成本。

## 目标

- 以一个仓库私有的编译期权威统一固定宽度 SIMD 级联、完整块判断、索引推进和标量尾部规则。
- 为 Core 与 Algorithms 分别生成程序集私有、可由 JIT 直接优化的展开代码，不新增运行时共享 SIMD 类型、调用或程序集依赖。
- 保持现有公开 API、数值语义、随机性、Repair/Evaluate 时机、状态所有权、硬件回退和确定性边界不变。
- 允许未来在明确声明能力、数值契约、测试与基准后增加 `float`、`int` 或新的加载/存储策略，而不要求复制固定宽度分派骨架。
- 以代码结构、JIT 反汇编、分配分析、局部基准和端到端基准共同验证零运行时开销，而不是仅凭生成发生在编译期作出性能结论。

## 非目标

- 不新增公共 SIMD API、运行时后端接口、用户配置、服务定位器、字符串注册、反射扫描或跨程序集共享缓冲区。
- 不改变 `ICandidateRepair`、`ContinuousProblem`、Optimizer、RunGroup 或标量单点评估契约。
- 不在本 Spec 中新增 `float`、`int` 的生产算法或 Repair；本次只定义将来显式扩展时必须满足的生成边界。
- 不引入 ISA 专属 X86/Arm API、GPU、SoA 布局、批量评估或新的向量宽度。
- 不建立可表达任意 C# 或任意 SIMD 算法的通用 DSL；生成输入只覆盖已批准热路径所需的有限结构。
- 不因为生成器能够统一修改就默认采用内存对齐、预取或其他优化；每项性能策略仍需独立行为分析和基准证据。
- 不删除标量参考。标量参考继续承担无 SIMD 硬件、最终尾部以及不能安全向量表达 lane 的权威语义。

## 架构契合

生成设施只属于仓库构建工具，不进入任何运行时包的公开或内部运行模型。它把源代码分别加入 Core 与 Algorithms 的编译；生成结果在命名空间、可见性和状态访问上仍属于消费程序集。Core 继续唯一拥有 Repair、边界数据和 Reflect 数值语义；Algorithms 继续拥有算法公式及其私有 `VectorOps`。生成器只拥有机械展开规则，不拥有 Position 边界、随机、评估、比较、算法状态或数值业务规则。

该边界保留 `Algorithms → Core` 的运行时依赖方向，也不建立 `Core → Algorithms` 或新的运行时公共后端。生成器不得把 Core 的 Reflect kernel 移入 Algorithms，也不得把算法公式移入 Core。生成输入必须是构建时可验证的显式声明；无效元素类型、缺失标量路径、不支持的运算能力或可能越界的声明必须在编译时产生诊断，不能静默生成降级代码。

ADR-0016 当前只授权 Algorithms 私有的固定宽度级联，SPEC-0004 则将 Reflect intrinsic 限定在 Core 私有实现。本 Spec 保留二者的运行时所有权，但新增了跨项目的编译期 SIMD 生成策略。Plan 必须比较运行时帮助器、链接共享源、构建前脚本和增量源码生成器；Plan 批准前必须以新 ADR 明确生成设施的所属层、项目引用形态、产物审查方式和重新评估条件。

## 信任与责任边界

| 数据或行为 | 责任方 | Core 是否验证 | 违反契约的结果 |
| --- | --- | --- | --- |
| 固定宽度顺序、硬件门和尾部骨架 | 编译期生成设施 | 否 | 生成器测试或消费项目编译失败；不得静默保留另一套手写生产路径。 |
| 运算公式、标量参考与特殊数值语义 | Core Repair 或对应 Algorithm | 按既有边界 | 保持既有测试、异常和数值兼容规则；生成器不得自行推导语义。 |
| 元素类型及其可用 SIMD 运算能力 | 每项生成声明与生成器诊断 | 否 | 不支持的组合编译失败，不以运行时检查或隐式转换补救。 |
| Position、边界形状与长度 | 调用方和 Core Repair | 是，保持既有验证 | 保持现有构造或 `Repair` 异常。 |
| Optimizer 工作区、随机流与调用时机 | 对应 Optimizer 与 `OptimizationRunContext` | 按既有协议 | 保持现有状态、确定性、Repair/Evaluate 和取消语义。 |
| SIMD 硬件可用性 | .NET 运行时与生成的固定宽度门 | 否 | 逐级缩窄到可用宽度，最终使用标量参考。 |
| 生成代码的运行时成本 | 维护者、JIT 和 Verification | 否 | 任一额外分派、分配或性能门槛失败时不得替换手写基线。 |

## 功能需求

### FR-001：单一固定宽度级联权威

- 前置条件：Core 或 Algorithms 中存在已批准并有实际调用者的固定宽度 SIMD 热路径。
- 触发行为：消费项目编译相应的显式生成声明。
- 预期结果：生成设施从单一权威产生 `Vector512<T> → Vector256<T> → Vector128<T> → scalar` 级联，包括每层硬件可用性、剩余长度、完整块条件、索引推进和最终标量尾部；消费代码不再手写同一分派骨架。
- 边界情况：长度小于最大硬件宽度时仍依次尝试较窄宽度；例如支持 512 位的机器上，7 个 `double` 必须按 4 + 2 + 1 处理。没有任何硬件向量宽度时整段使用标量参考。
- 验收标准：生成器单元/快照测试覆盖每种宽度组合与长度 0、1、2、7、8、15、16；仓库残留审查确认纳入范围的生产路径不存在第二套手写级联。

### FR-002：程序集私有的完全展开输出

- 前置条件：Core 或 Algorithms 引用仓库私有生成设施并提供有效声明。
- 触发行为：编译器执行生成并编译输出。
- 预期结果：生成类型和成员只在消费程序集内部可见，直接使用该程序集已有的私有状态、标量参考和运算语义；运行时包不引用或加载生成器程序集，不通过 delegate、接口、反射、函数指针、策略对象或跨程序集 SIMD Helper 执行块循环。
- 边界情况：Core 与 Algorithms 可消费相同机械生成策略，但不得共享运行时状态、边界数据、算法公式或生成后的类型。
- 验收标准：项目引用和发布产物审查证明生成器仅为编译期依赖；API 差异检查无新增公开符号；IL/JIT 审查无生成器相关运行时调用。

### FR-003：运算语义由消费方显式定义

- 前置条件：一项热路径需要生成一个或多个固定宽度块体。
- 触发行为：维护者声明该运算的输入、输出、块体、归约或 lane 修补需求以及标量参考。
- 预期结果：生成设施只展开声明中明确存在的运算，不从方法名称、运行时类型扫描或任意源代码重写推断业务语义。Reflect 的边界加载、掩码和危险 lane 修补继续属于 Core；PSO/Firefly 的公式、归约和 Span 所有权继续属于 Algorithms。
- 边界情况：逐元素写回、按宽度归约、原位更新和写回后逐 lane 标量修补具有不同生命周期，生成模型必须显式区分；不能用一个带运行时回调的循环掩盖差异。
- 验收标准：对每个纳入路径均可从生成声明追踪到既有 Spec 的标量/数值契约；差分测试覆盖特殊值、重叠规则、归约顺序边界和危险 lane。

### FR-004：元素类型与能力显式扩展

- 前置条件：后续已批准 Spec 需要在某项运算中增加 `double` 之外的元素类型或新的加载/存储策略。
- 触发行为：维护者为该运算显式启用类型和所需能力。
- 预期结果：生成设施按 `Vector512<T>.Count`、`Vector256<T>.Count` 和 `Vector128<T>.Count` 产生正确块宽；浮点有限性、除法、截断、整数溢出、归约等能力必须逐项声明，不能假定替换 `T` 后语义自然成立。
- 边界情况：不支持某运算的类型、宽度或目标框架必须产生编译诊断；不得自动转为另一元素类型或在热路径加入通用运行时判断。
- 验收标准：生成器负面测试证明不支持的类型/能力组合编译失败；任何新生产 specialization 由独立 Spec、行为测试和性能 Verification 准入。

### FR-005：确定且可审查的生成结果

- 前置条件：相同仓库版本、SDK、目标框架、生成声明和构建属性。
- 触发行为：本地或 CI 重复构建。
- 预期结果：生成输出确定、格式稳定、带可定位的生成来源，并可在代码审查和失败诊断中查看；生成器不得读取网络、时间、机器路径或未声明环境状态决定输出。
- 边界情况：声明冲突、重复 hint name、缺失模板、无标量参考或不支持能力必须产生带声明位置的编译诊断。
- 验收标准：生成器确定性测试、快照测试、消费项目编译测试和 CI 生成残留检查通过；相同输入产生逐字节相同的生成文本。

### FR-006：彻底替代而非双路径保留

- 前置条件：某个现有手写 SIMD 热路径通过全部行为和性能门槛。
- 触发行为：生成路径进入生产实现。
- 预期结果：删除被替代的手写宽度级联和仅为迁移存在的转发/兼容代码，只保留具有独立语义职责的标量参考、运算声明和必要的消费方 kernel 内容；不得保留运行时开关在新旧实现之间选择。
- 边界情况：任一门槛失败时保留当前手写生产实现并删除候选生成接入，不提交两套长期实现。
- 验收标准：残留搜索、实现审查和调用图证明每项生产运算只有一个 SIMD 路径和一个有独立职责的标量参考。

## 非功能需求

### NFR-001：零运行时抽象开销

- 测量方式：比较生成候选与当前手写基线的 Release IL、JIT 反汇编、控制流、调用、边界检查、加载/存储和分配；在相同机器、Runtime、JIT 设置和输入上运行 BenchmarkDotNet。
- 可接受阈值：生成路径不得新增运行时对象、托管分配、delegate、接口/虚调用、反射、共享状态或每块额外分派；未改变语义的 `double` specialization 必须与手写基线具有结构等价的 JIT 代码。局部与端到端主要基准均不得出现统计上可确认的回退。
- 证据类型：IL/JIT 反汇编、BenchmarkDotNet、MemoryDiagnoser、实现审查。

### NFR-002：数值、状态与确定性兼容

- 测量方式：复用并扩展 SPEC-0004 与 SPEC-0005 的差分、特殊值、固定 seed、随机调用次数、Repair/Evaluate 时点、重复 run、并发隔离和分配测试。
- 可接受阈值：除既有 Spec 已批准的 ULP 或跨目标执行环境差异外，生成路径不得引入新的数值容差、随机序列、状态、异常、调用时机或公开行为差异。
- 证据类型：自动化测试、固定环境重复运行、实现审查。

### NFR-003：性能准入与报告

- 测量方式：对 Reflect、PSO 和 Firefly 分别运行既有代表性局部与端到端 BenchmarkDotNet，比对当前手写基线与生成候选；记录硬件宽度、Runtime、JIT、输入规模和分配。
- 可接受阈值：每项被替代路径都满足 NFR-001；任一主要比较回退或新增分配时不得合入该替换。Verification 按 `基线耗时 / 生成后耗时` 简短报告局部和端到端比率，不将单机结果外推为通用承诺。
- 证据类型：BenchmarkDotNet、MemoryDiagnoser、Verification 报告。

### NFR-004：有限的构建复杂度

- 测量方式：审查生成模型、项目引用、诊断、测试数量、增量输入和完整/增量构建表现。
- 可接受阈值：生成设施不解析任意 C# 文本、不建立通用表达式语言、不访问网络或运行生产代码；输入模型只覆盖实际调用者需要的有限 SIMD 结构。无关源文件变化不得改变生成文本，生成器不得使 IDE/CI 构建出现无法定位的非确定失败。
- 证据类型：生成器单元测试、增量测试、项目引用审查、CI 构建。

## 职责与替代关系

- 新增的概念：仓库构建工具拥有的私有 SIMD 生成设施；显式运算生成声明；确定且可审查的程序集私有生成源。
- 被替代的概念：纳入范围的 Core/Algorithms 热路径中重复手写的固定宽度硬件门、完整块循环、索引推进、宽度缩窄和标量尾部骨架。
- 必须删除的旧行为或公共入口：不删除公共入口；删除通过门槛后的手写级联、迁移转发层、兼容壳和任何新旧运行时选择开关。
- 明确保留的旧概念及独立理由：Core 的 Reflect 数值 kernel、边界数据与标量参考；Algorithms 的公式、归约语义、私有工作区与标量参考；它们各自拥有生成器不能推断的业务和数值职责。
- 完成后每个概念的唯一所属层：构建工具拥有机械生成规则；Core 拥有 Repair 语义及其生成结果；Algorithms 拥有算法算术及其生成结果；Tests 定义兼容性；Benchmarks 与 Verification 记录零开销和性能证据。

## 成功标准

- 固定宽度顺序、硬件门或尾部策略的统一修改只需变更一个编译期权威，并同步反映到所有纳入的 Core/Algorithms 生成路径。
- Core 与 Algorithms 的运行时包、公开 API、依赖方向、职责、随机性、状态和数值契约保持不变。
- 生成路径没有可观察的运行时抽象成本、没有新增分配，并在既有局部与端到端主要基准中不劣于手写基线。
- 被替代的重复手写级联彻底删除，标量参考和消费方业务语义仍清晰可审查。
- 未来元素类型或加载策略只能显式加入并独立验证，不会因通用模板自动扩大行为范围。

## 假设与已澄清决定

- 已确认：首期同时生成外层固定宽度级联和现有运算的三宽度机械展开；消费方继续手写标量参考及 Reflect/算法特有语义。
- 已确认：首期生产 specialization 仅迁移现有 `double` 路径；`float`、`int` 和内存对齐只验证扩展模型与负面诊断，不新增生产调用者。
- 已确认：“零性能开销”采用 NFR-001 的可执行定义：无额外运行时结构，JIT 代码结构等价，且 BenchmarkDotNet 无可确认回退；不要求不同 SDK/JIT 构建产生逐字节相同机器码。
- 待 Plan 决定：生成输入的最小表示、生成源落盘/审查方式、生成器项目目标框架和编译期引用形态。Plan 必须比较增量源码生成器、链接共享源与构建前模板脚本，不能因本 Spec 标题预先跳过方案证据。
